# 产品与企业采用评价框架

**版本：** v0.1  
**适用对象：** AI Coding Agent 产品及其具体工作流

## 1. 评价原则

本框架用于形成可比较、可解释的研究记录，不用于制造脱离场景的绝对排名。

- 评分对象是“产品在特定版本、套餐、入口和任务下的表现”。
- 官方功能存在不等于实际效果稳定，必须区分功能可用性与结果质量。
- 未测试、无法访问或证据不足时填写 `N/A`，不得用中间分代替。
- 总分只用于同类产品、相近场景的辅助比较，结论必须回到用户需求和组织约束。
- 每个维度同时记录评分、证据、采集日期和置信度。

## 2. 评分尺度

采用 0—5 分：

| 分数 | 定义 |
|---:|---|
| 0 | 不提供该能力，或在目标场景中不可用 |
| 1 | 能力非常有限，需要大量人工补救 |
| 2 | 可完成简单任务，但稳定性或适用范围明显受限 |
| 3 | 在常见任务中基本可用，仍需要持续监督 |
| 4 | 在复杂任务中表现较稳定，具备较完整的执行和验证闭环 |
| 5 | 在目标场景中达到领先且可重复的水平，证据充分 |
| N/A | 未测试、不可访问或证据不足 |

建议保留 0.5 分，但必须解释评分差异。

## 3. 一级评价维度

### A. 任务理解与规划（15%）

关注产品是否能够把模糊目标转化为可执行计划。

- 需求理解准确性
- 主动澄清能力
- 任务拆解质量
- 约束识别与风险提示
- 计划与实际执行的一致性

### B. 代码库理解与上下文管理（15%）

- 仓库结构识别
- 跨文件与跨模块关系理解
- 依赖、接口和数据流追踪
- 长上下文保持
- 对项目规则、文档和历史决策的利用
- 上下文选择是否精准，是否引入无关信息

### C. 执行与工具调用（15%）

- 文件创建和修改
- 终端、包管理器和构建工具调用
- 版本控制操作
- 外部工具或协议扩展
- 多步骤任务连续执行
- 权限控制和危险操作处理

### D. 结果质量与变更控制（15%）

- 功能正确性
- 代码可读性与可维护性
- 与现有架构和风格的一致性
- 变更范围控制
- 是否引入非必要重构
- 对兼容性、迁移和边界条件的处理

### E. 验证、Review 与错误恢复（15%）

- 自动运行测试和静态检查
- 根据失败信息迭代修正
- Code Review 能力
- 安全、依赖和许可证检查
- 对失败原因的解释
- 是否提供可审查的证据与变更摘要

### F. 人机协作与可控性（10%）

- 关键决策点是否透明
- 用户能否限制范围、工具和权限
- 中途干预和恢复能力
- 计划、日志和差异展示
- 对不确定性的表达
- 是否容易出现越权修改或失控循环

### G. 扩展、集成与工作流适配（5%）

- IDE、CLI、GitHub/GitLab 等入口
- MCP、插件、Skills、Rules 或自定义指令
- CI/CD 与项目管理工具集成
- 自定义模型或模型选择
- 团队模板和组织级配置

### H. 企业治理与安全（5%）

- 数据使用和保留政策
- 权限、身份和访问控制
- 审计日志
- 私有部署或云平台选择
- 合规、安全扫描和策略控制
- 管理后台与组织级用量管理

### I. 成本与使用效率（5%）

- 价格结构透明度
- 额度、积分或按量计费的可预测性
- 完成有效任务的实际成本
- 等待时间和并行能力
- 人工监督及返工成本

## 4. 场景化评价

同一产品至少区分以下任务类型，避免将不同能力压缩为一个分数：

1. **Repository Q&A：** 理解陌生代码库并回答问题；
2. **Bug Fix：** 定位问题、修改代码并通过测试；
3. **Feature Implementation：** 根据需求完成跨文件功能；
4. **Refactor / Migration：** 保持行为的结构调整或依赖升级；
5. **Code Review：** 识别缺陷、风险和改进点；
6. **Greenfield App：** 从需求到可运行应用；
7. **Documentation / Tests：** 生成并验证文档、测试和辅助资产；
8. **Long-running Delegation：** 长时间异步或自主任务执行。

## 6. 评分计算

建议计算三个层级：

1. **维度分：** 对该维度指标求平均；
2. **场景分：** 在特定任务中按权重计算；
3. **适配结论：** 根据用户类型和组织约束给出推荐或不推荐理由。

不建议在样本不足时发布跨产品总榜。若必须展示综合分，应同时满足：

- 使用相同任务和相近权限；
- 标注模型、套餐、版本和测试日期；
- 每个产品至少完成 3 次独立任务；
- 展示方差、失败案例和未覆盖能力；
- 不把 0.1—0.2 分差异解释为显著领先。

## 7. 用户价值评价

技术能力之外，还需回答：

- 产品节省了哪类工作时间？
- 是否减少了认知负担、沟通成本或重复操作？
- 是否增加了审查、修复或治理成本？
- 对新手和专家的价值是否不同？
- 对个人项目和企业代码库的价值是否不同？
- 产品创造的价值来自模型能力，还是来自工作流和集成？

## 8. 企业采用成熟度

将企业使用分为五级：

| 等级 | 状态 |
|---:|---|
| 1 | 个人自发试用，缺少统一政策 |
| 2 | 团队试点，限制数据和任务范围 |
| 3 | 建立采购、权限、培训和基本评估流程 |
| 4 | 接入代码库、CI、项目管理和审计体系 |
| 5 | 形成组织级 Agent 平台、评测体系和持续治理机制 |

对产品的企业能力评价，应说明其适合支持哪一级成熟度，而不是仅罗列安全认证。

## 9. 证据要求

每个评分至少关联一条证据：

- 官方文档或产品说明；
- 实际测试记录；
- 可复现评测；
- 公开客户案例；
- 安全或治理文档；
- 公开定价与套餐说明。

仅有营销口号时，不应给出高置信度评分。
