# 研究设计 v1.0

> 状态：已由作者确认通过（2026-07-30）  
> 重要修订：删除原 RQ6；字节目标岗位仅作为研究结论的应用案例，不作为独立研究问题。

## 1. 研究题目

**从代码辅助到 Agent 系统：AI Coding 产品演进如何重塑组织能力与人才需求**

副标题：**基于产品资料、公开招聘岗位与个人实践案例的探索性研究**

## 2. 研究目的

本研究考察：当 AI Coding 产品从代码补全和对话式辅助工具，演进为能够规划、调用工具、操作环境、验证结果并持续交付的 Agent 系统时，企业面临的关键能力瓶颈发生了什么变化，以及这些变化如何反映在组织职能、岗位设计和人才识别方法中。

预期形成三类成果：

1. 对 AI Coding Agent 产品及行业变化的解释；
2. 对相关岗位和组织能力变化的分析；
3. 一套从业务能力瓶颈出发的人才 Mapping 方法。

人才 Mapping 是研究结论之一，而不是研究起点。字节目标岗位仅用于检验研究结论对真实人才战略工作的适用性。

## 3. 研究问题

### 主研究问题

> **AI Coding Agent 的产品能力演进，正在如何改变企业的组织能力瓶颈、岗位组合和人才需求？**

### RQ1：产品发生了什么变化？

AI Coding 产品是否正从代码补全、对话问答和单次代码生成，演进到：

- 仓库级理解；
- 任务规划；
- 工具和命令调用；
- 环境操作；
- 长任务与异步执行；
- 多 Agent 协作；
- 自动测试与验证；
- 企业权限、审计与治理。

### RQ2：能力瓶颈是否发生迁移？

代码生成能力增强后，企业的关键困难是否逐渐转向：

- 任务与价值定义；
- 环境和工具集成；
- 异常恢复；
- 评测与验证；
- 权限和安全；
- 企业部署；
- 用户采用；
- 跨职能协作。

### RQ3：组织和岗位如何响应？

企业是否为上述问题建立了新的岗位、团队或职能组合，例如 Agent Harness、Evals、模型性能产品、Deployed Product Manager、AI Adoption、Agent Security、AI Enablement、People Research 和 AI 人才战略等。

### RQ4：传统岗位标签是否足够？

岗位名称、专业和工作年限能否准确解释候选人的实际能力；人才团队是否还应考察候选人解决过的问题、服务过的产品能力、产生的可验证结果，以及连接技术、产品、用户和组织的能力。

### RQ5：人才 Mapping 应如何调整？

人才战略团队能否采用以下链条补充传统 Mapping：

> **产品路线 → 能力瓶颈 → 组织能力 → 岗位组合 → 人才来源 → 候选人证据**

## 4. 待验证命题

以下均为研究假设，不得预先写成结论。

### H1：项目可行边界扩张

AI Coding Agent 不只加快原本会做的软件开发，也可能使原本不会编程的人启动过去不会考虑的项目。

### H2：能力瓶颈迁移

代码生成能力增强后，瓶颈可能转向需求定义、环境集成、验证治理、企业部署和采用。

### H3：岗位名称解释力下降

相同岗位名称在不同公司可能承担完全不同的产品能力；不同岗位名称也可能解决相同的能力瓶颈。

### H4：连接型人才需求上升

随着 Agent 进入真实业务，企业可能更需要能够连接模型、技术系统、用户需求、商业价值和组织执行的人才。

### H5：技术能力发生结构性变化

对于部分非核心研发岗位，技术要求可能从“亲自完成全部编码”转向理解系统结构、判断技术可行性、制作和验证原型、识别风险并对技术选择负责。这不意味着专业工程人才不再重要。

### H6：Agent 治理成为组织能力

随着 Agent 获得更大执行权限，企业可能需要建立类似数字内部控制的机制，包括权限分级、职责分离、人工审批、独立验证、审计证据、停止和回滚，以及责任归属。

## 5. 研究边界

### 5.1 时间范围

主要观察 **2024-01 至 2026-07-30**。更早资料只用于背景说明，不直接代表当前状态。

### 5.2 地域范围

目标比例为中国公司和产品约 60%、国际公司和产品约 40%。不为满足配额而使用无法核验的资料。

### 5.3 产品样本

核心产品：

- OpenAI Codex
- Anthropic Claude Code
- Cursor
- Qoder
- GitHub Copilot
- Cognition Devin

参考产品根据证据质量选择 3—5 个：

- 字节 TRAE
- 腾讯 CodeBuddy
- Replit Agent
- OpenCode
- 其他具有代表性的企业 Agent 或开发者工具

WorkBuddy、Hermes 等主要作为个人使用经验，不当然纳入核心行业样本。

### 5.4 岗位范围

重点研究：Agent 研发与平台、Agent Harness、Evals 与模型质量、AI 产品和策略产品、用户研究、Developer Experience、Deployed PM、AI Adoption、解决方案架构、安全与治理、AI Enablement、People Research、Workforce Planning、AI 人才战略与人才情报。

### 5.5 明确排除

本研究不做：

- AI Coding 产品性能排行榜；
- 单纯模型能力对比；
- 针对具体个人的人才名单；
- 非公开个人信息搜集；
- 公司内部组织架构推测；
- 为字节制定完整招聘作战方案；
- 用一两个案例证明整个行业趋势。

## 6. 分析单位

1. **产品能力变化**：产品新增或强化了什么能力，以及试图解决什么问题；
2. **公开招聘岗位**：岗位承担的实际任务、产出和能力要求；
3. **公司级组织信号**：特定时期公开招聘所释放的人才需求信号，不等同于完整组织架构；
4. **个人一手案例**：用于展示机制和一手体验，不用于估算行业比例或证明普遍因果关系。

## 7. 资料来源与证据等级

### 7.1 来源优先级

产品资料优先使用官方文档、发布说明、技术博客、研究文章和开发者文档。岗位资料优先使用公司官方招聘网站和官方 ATS。外部验证使用学术论文、权威研究机构、可核验行业报告和高质量访谈。

### 7.2 证据等级

- **A 级：直接官方证据**——可从官方完整文本确认功能、职责、要求或公司观点；
- **B 级：不完整但可确认的官方证据**——例如仅能确认岗位名称或产品方向；
- **C 级：外部补充证据**——需要交叉核验；
- **D 级：研究者推断**——必须使用“可能说明”“初步支持”“尚不能证明”等表述；
- **E 级：个人案例**——单独标注为一手案例。

事实、公司主张、研究推断和个人经验必须分开呈现。

## 8. 岗位编码方法

### 8.1 开放编码

第一遍阅读 JD 时不套入预设模型，直接记录：

- 岗位解决什么问题；
- 主要工作对象；
- 交付结果和成功指标；
- 协作对象；
- 技术能力深度；
- 是否涉及用户、商业、验证、安全或部署；
- 专业和职业背景限制。

### 8.2 结构化编码字段

| 字段 | 含义 |
|---|---|
| 产品路线 | IDE、Agent 平台、云端 Agent、企业部署等 |
| 能力瓶颈 | 执行、验证、安全、采用、价值等 |
| 岗位族群 | 工程、产品、评测、部署、安全、人才等 |
| 关键任务 | 岗位实际负责的工作 |
| 结果指标 | 完成率、质量、采用率、收入、效率等 |
| 技术深度 | 基础理解、技术判断、原型能力、核心研发 |
| 用户与业务接触 | 是否直接研究用户或客户 |
| 治理要求 | 权限、安全、审计、验证、责任 |
| 背景门槛 | 专业、年限、行业经历 |
| 可迁移来源 | 哪些相邻经历可能解决同类问题 |
| 证据等级 | A、B、C、D |
| 原文依据 | 可追溯的岗位或产品原文 |

## 9. 六维能力候选框架

六维模型定位为**候选分析框架**，不是已被证明的行业标准：

- V：价值判断
- P：产品定义
- T：技术判断
- A：Agent 编排
- G：验证治理
- O：组织连接

每项采用三级编码：

- 0：没有相关证据；
- 1：间接涉及或属于辅助要求；
- 2：明确属于核心职责或主要识别标准。

每个分值必须附原文或明确依据。编码顺序为：开放编码 → 冻结定义 → 六维编码 → 隔离上下文复核 → 争议项人工讨论。

## 10. 样本设计

### 10.1 产品样本

6 个核心产品，3—5 个参考产品。每个核心产品至少收集官方定位、关键功能变化、企业能力、评测或治理设计以及与其他路线的差异。

### 10.2 岗位样本

目标收集 **40—60 份公开 JD**：

| 岗位类别 | 目标数量 |
|---|---:|
| Agent 核心研发与平台 | 10—14 |
| 评测与质量 | 6—10 |
| AI 产品与用户研究 | 8—12 |
| 企业部署与采用 | 6—10 |
| 安全与治理 | 4—8 |
| 人才与组织研究 | 4—8 |

该样本用于探索不同能力瓶颈，不用于推断整个劳动力市场的统计占比。

### 10.3 边界与反例样本

主动纳入：

- 明确要求深厚计算机背景的核心工程岗位；
- 名称新颖但职责仍近似传统售前的岗位；
- 不要求组织连接的纯研究或纯执行岗位；
- 高度依赖专业资质的安全与基础设施岗位。

## 11. 分析步骤与交付物

1. **产品能力演进**：产出产品能力演进矩阵；
2. **能力瓶颈迁移**：产出“功能变化—新增风险或摩擦—组织能力”矩阵；
3. **岗位和组织响应**：产出岗位族群与组织职能图；
4. **人才能力组合**：检验六维模型及反例；
5. **人才 Mapping 方法**：形成“能力瓶颈—岗位—直接来源—相邻来源—候选人证据”方法；
6. **字节岗位应用**：仅作为应用章节，解释研究结论与目标岗位的关联；
7. **个人案例**：校园重建工具和 Movie Night 仅用于机制说明。

## 12. 最终报告结构

1. 研究背景与问题
2. 研究方法与证据边界
3. AI Coding 产品的 Agent 化演进
4. 从代码生产到系统交付的瓶颈迁移
5. 企业岗位与组织能力变化
6. 连接型人才与能力组合
7. 从岗位标签到能力瓶颈的人才 Mapping
8. 对 AI 组织能力情报岗位的应用启示
9. 个人实践案例
10. 结论、边界与后续问题

第 8 章属于应用章节，建议约占正文 15%—20%；第 9 章约占正文 10%。

## 13. 质量控制规则

1. 事实、公司主张、个人经验和研究推断分开标注；
2. 每项岗位判断保留原始 JD 依据；
3. 不从产品功能直接推断公司真实组织架构；
4. 不将招聘数量直接等同于能力重要程度；
5. 不使用定向样本频次代表整个行业占比；
6. 主动寻找反例；
7. 对关键岗位进行隔离上下文二次编码；
8. 公开资料缺失时明确写“不足以判断”；
9. 个人案例不用于证明行业普遍结论；
10. 所有阶段先由作者审核，再进入正式报告。

## 14. 阶段性交付

1. 产品能力演进矩阵；
2. 能力瓶颈矩阵；
3. 15—20 份代表性 JD 的开放编码；
4. 六维复核与反例；
5. 人才 Mapping 方法；
6. 完整报告草稿；
7. 经确认后进入正式发布版本。

## 15. 研究定位

本研究不是“哪些公司有值得某家公司招聘的人”，而是：

> **AI Coding Agent 的产品演进产生了哪些新的组织能力问题，企业正在使用什么岗位和人才组合解决这些问题，以及人才战略团队应当如何理解和识别这些能力。**
