# 六维能力组合框架 v0.2

> 状态：作者已确认并冻结，用于交付四的第二遍编码  
> 更新时间：2026-07-30  
> 定位：连接能力瓶颈、岗位职责与候选人证据的角色能力描述语言，而非总分量表或行业标准。

## 1. 框架结构

框架由四层构成：

1. **六个主能力维度**：V、P、T、A、G、O；
2. **专业与方法标签**：说明能力应用于哪个专业领域；
3. **情境与责任标签**：M、D、C；
4. **证据标记**：E、I、NA。

禁止将各维度简单相加后用于岗位或候选人总体排名。

## 2. 六个主维度

### V：价值选择与优先级

在目标、资源、风险和时间约束下判断为什么做、做什么、先做什么，以及成本、质量、安全和增长之间如何取舍。

- V=2：明确负责场景选择、战略、优先级、资源分配或业务结果；
- V=1：参与价值判断，但不拥有最终优先级；
- V=0：仅执行既定任务。

边界：V决定“做什么、为什么做”；P负责把所选方向转化为可执行定义。

### P：问题结构化与产品定义

把模糊需求、用户问题或业务目标转化为场景、产品行为、工作流、规格、路线图和验收标准。

- P=2：拥有需求、产品方向、路线图或工作流定义责任；
- P=1：为产品定义提供重要输入；
- P=0：仅进行技术架构或实现既定需求。

技术架构设计不得自动编码为产品定义。

### T：技术判断与系统理解

理解技术系统或专业方法的结构、约束和失败方式，并判断可行性、架构、集成、性能、成本、可靠性与风险。

- T=2：亲自设计、建设复杂系统或作关键技术判断；
- T=1：需要可信的技术、数据或方法判断，但不建设核心系统；
- T=0：不需要实质技术或专业方法判断。

T必须附专业领域标签，例如：

- `T2[Agent Harness]`
- `T2[分布式平台]`
- `T2[安全/IAM]`
- `T2[评测工程]`
- `T1[People Science/统计]`
- `T2[企业技术集成]`

### A：Agent系统设计与工作流编排

A拆分为两个子码：

#### A-S：Agent System

设计或建设Agent循环、工具调用、模型路由、Context、Memory、会话与任务生命周期、沙箱、多Agent系统或控制平面。

#### A-W：Agent Workflow

在实际工作中拆分任务、选择Agent或模型、分配工具和权限、设计执行顺序、设置审批点、处理中断与升级并汇总结果。

记录方式：`A=(A-S, A-W)`。

### G：证据验证与风险控制

G拆分为两个子码：

#### G-E：Evidence and Evaluation

关注结果是否有证据支持，包括评测、测试、数据集、实验、评分器、回归检测、用户研究、心理测量、质量指标和完成标准。

#### G-R：Risk and Control

关注执行是否处于可接受控制范围，包括权限、身份、Secrets、审批、安全边界、审计、发布控制、停止条件、回滚和责任归属。

记录方式：`G=(G-E, G-R)`。禁止将两个子码重新相加形成治理总分。

### O：边界转换与组织推动

在不同知识体系、职能或利益相关者之间完成需求翻译、目标对齐、权责安排、冲突处理、采用推动和结果闭环。

- O=2：跨边界转换与推动本身是岗位主要交付；
- O=1：需要常规跨团队协作，但主要交付仍是专业成果；
- O=0：基本在单一专业边界内完成工作。

普通“跨团队合作”不能自动编码为O=2。

边界：V负责目标和优先级，O负责使不同主体围绕目标完成行动。

## 3. 横向标签

### M：研究与测量方法

- M0：不依赖正式研究或测量方法；
- M1：使用既有指标、数据或研究结果；
- M2：设计实验、数据集、访谈、测评、评分器或统计模型。

### D：端到端交付责任

- D0：提供建议或局部产物，不负责最终结果；
- D1：对部分流程或共享结果负责；
- D2：对从问题定义到上线、采用、发布或结果闭环负责。

### C：客户与商业情境

- C0：基本不直接面对客户或商业结果；
- C1：偶尔接触客户需求或商业团队；
- C2：客户价值、采用、扩展或商业结果是主要工作对象。

M、D、C均不参与总分。

## 4. 证据标记

每项编码同时标记证据类型：

- `2E`：核心能力，官方JD直接明确；
- `1E`：辅助能力，官方JD直接明确；
- `1I`：由交付物和职责支持的研究者推断；
- `0`：材料完整，未发现相关证据；
- `NA`：资料不足，不能判断。

0与NA必须严格区分。资料不完整的岗位不得因缺少信息而记为0。

## 5. 标准画像表达式

岗位画像采用能力组合表达式，不使用总分。例如：

- Agent Harness工程师：`T2[Agent系统/平台] + A-S2 + A-W1 + G-E1 + G-R1 + O1；D2`
- Agent评测工程师：`T2[评测工程] + G-E2 + A-S1 + O1；M2，D2`
- Codex安全产品经理：`V1 + P2 + T2[安全/IAM] + A-S1 + G-R2 + O2；D2，C1`
- AI Adoption Engineer：`V2 + P1 + T2[开发者工具/集成] + A-W1/2 + G-E1 + O2；D2，C2`
- People Research Scientist：`V1 + T1[People Science/统计] + G-E2 + O2；M2，D1`
- Workforce Planning Lead：`V2 + T1[数据与规划] + G-E1 + G-R1 + O2；M1，D2`

## 6. 使用限制

本框架：

- 可以描述岗位能力组合；
- 可以连接能力瓶颈、岗位职责和候选人证据；
- 可以帮助识别直接与相邻人才来源；
- 不得作为人格模型；
- 不得作为通用胜任力总分；
- 不得代替专业领域判断；
- 不得仅凭岗位名称编码；
- 不得用于证明“连接型人才适用于所有Agent岗位”。

## 7. 交付四的后续检验

使用本框架重新编码17份A级完整JD，并检查：

1. A-S与A-W是否减少“建设Agent平台”和“使用Agent工作流”的混淆；
2. G-E与G-R是否减少评测人才和风险控制人才的混淆；
3. T-Domain是否阻止不同专业技术能力被错误视为可替代；
4. O=2的严格标准是否减少普通协作被误认为连接能力；
5. M、D、C标签是否补足研究方法、结果责任和客户情境；
6. 仍有哪些岗位无法被框架合理表达。
