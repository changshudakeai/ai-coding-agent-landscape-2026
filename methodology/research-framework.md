# 研究框架（Research Framework）

**版本：** v0.1  
**研究快照日期：** 2026-07-30

## 1. 研究目标

本研究不以制作单一“产品排行榜”为目标，而是建立一个能够解释以下问题的分析框架：

- AI Coding Agent 在软件开发价值链中承担哪些任务；
- 不同产品分别服务哪些用户、场景和组织约束；
- 产品能力、工作流入口、模型、生态与企业治理如何共同构成竞争优势；
- AI Coding Agent 产业需要哪些人才，以及岗位能力要求如何组合。

最终产出应同时具备三种用途：

1. **行业研究：** 解释产品生态和竞争格局；
2. **产品研究：** 支持产品选型、用户需求分析和能力边界判断；
3. **人才研究：** 支持岗位分类、目标公司 Mapping 和能力标签设计。

## 2. 核心概念

### 2.1 AI Coding Assistant

以补全、问答、代码解释或局部编辑为主，通常由用户持续驱动每一步操作。

### 2.2 AI Coding Agent

能够围绕目标进行多步骤规划与执行，并调用代码库、终端、测试、版本控制或外部工具完成任务；其输出需要通过人工或自动化机制验证。

### 2.3 Agentic Development Workflow

将需求、上下文、执行权限、验证机制和人工决策点组合成可重复的软件开发流程，而非仅依赖一次提示词生成代码。

> 注：产品可能同时包含 Assistant 与 Agent 模式。本研究按具体功能和工作流分析，不按营销名称直接归类。

## 3. 研究问题

### 3.1 产品与技术

- 产品覆盖需求分析、设计、编码、测试、Review、部署和维护中的哪些环节？
- 在大型代码库理解、多文件修改、工具调用、测试闭环和长任务执行方面表现如何？
- 产品的主要失败模式是什么，用户需要承担多少监督和返工成本？
- 模型能力、上下文工程、工具链、Agent Runtime、评测体系和交互入口分别贡献了什么价值？

### 3.2 用户与场景

- 独立开发者、企业工程师、产品经理、非专业开发者和内部效率团队的目标有什么差异？
- 用户选择产品时最重视哪些因素：效果、速度、可控性、价格、安全、生态还是学习成本？
- 哪些任务适合完全委派，哪些任务需要人主导关键决策？
- 导致用户不信任、停止使用或限制使用 Agent 的主要原因是什么？

### 3.3 公司与竞争

- 模型厂商、代码托管平台、IDE/开发工具公司、云平台和独立创业公司分别掌握哪些资源？
- 产品如何通过入口、模型、数据、分发、企业客户、插件生态和工作流集成构建壁垒？
- 开源与闭源产品在成本、可控性、部署和生态方面如何取舍？
- 企业采用从个人工具扩展到组织级平台时，会出现哪些治理需求？

### 3.4 人才与组织

- AI Coding Agent 相关业务包含哪些岗位族群？
- 产品、工程、研究、解决方案、开发者关系和人才战略岗位分别需要哪些能力？
- 哪些能力属于通用能力，哪些属于稀缺或阶段性能力？
- 不同类型公司和不同发展阶段对人才背景的偏好如何变化？

## 4. 分析单位

本研究区分四类分析单位，避免将产品、功能、公司和岗位混为一谈：

1. **Product：** 可独立采购、使用或部署的产品；
2. **Capability：** 产品中的具体能力或工作流；
3. **Company：** 产品背后的公司及其战略资源；
4. **Role / Job Posting：** 公开岗位及其职责、能力和背景要求。

## 5. 研究范围

### 5.1 纳入范围

- 面向软件开发、代码维护或应用构建的 AI Agent；
- IDE、CLI、代码托管平台和云端异步执行等主要入口；
- 面向个人、团队和企业的商业产品，以及具有代表性的开源工具；
- 与产品、Agent 工程、开发者工具、企业效率和人才战略有关的公开岗位。

### 5.2 暂不纳入

- 仅提供基础模型 API、但没有明确 Coding Agent 工作流的模型；
- 仅做普通代码补全、缺少多步骤执行能力的传统插件；
- 无法验证来源的传闻、匿名爆料和非公开组织信息；
- 私人联系方式、家庭信息等与职业研究无关的个人数据。

## 6. 初始样本策略

采用分层目的抽样，而不是按知名度简单罗列产品。

### Tier A：重点案例

满足以下至少两项：

- 在产品形态或商业模式上具有代表性；
- 有较完整的官方文档和公开材料；
- 能进行实际试用或获得可验证的一手观察；
- 在企业采用、开发者生态或人才招聘方面具有研究价值。

### Tier B：对照案例

用于补充开源、区域市场、垂直场景或不同交互入口，不强制进行同等深度的完整测试。

### 产品形态分层

- IDE / AI-native editor
- CLI / terminal agent
- Repository / cloud coding agent
- Autonomous software engineering agent
- Browser-based app building agent
- Open-source and self-hostable agent
- Enterprise developer platform

样本清单在 `data/product-mapping.csv` 中维护。纳入样本不代表推荐，产品状态和归类必须在调研后确认。

## 7. 研究方法

### 7.1 桌面研究

收集并核对：

- 官方产品页、文档、更新日志、价格与安全说明；
- 公司公告、工程博客和公开演讲；
- 官方招聘页面与公开职位描述；
- 学术论文、公开评测和可复现实验；
- 高质量用户案例与开发者反馈。

### 7.2 产品体验记录

对可实际使用的产品，记录统一任务下的：

- 任务理解和澄清行为；
- 计划质量与执行路径；
- 多文件和跨模块修改；
- 工具调用、测试与错误恢复；
- 人工干预次数与返工原因；
- 输出证据、可审查性和最终结果。

个人体验属于一手观察，但不能自动推广为所有用户的普遍结论。

### 7.3 岗位内容分析

对公开岗位进行结构化编码：

- 岗位族群和职级；
- 职责主题；
- 技术、产品、商业和研究能力；
- 教育、行业和工作经历偏好；
- AI 工具使用或开发要求；
- 语言、地点和协作要求。

岗位样本应记录采集日期和原始链接；失效岗位保留快照状态，不继续视为当前招聘需求。

### 7.4 三角验证

重要结论原则上至少由两类证据支持，例如：

- 官方功能说明 + 实际试用；
- 官方招聘岗位 + 多个岗位样本归纳；
- 公司公告 + 可验证的产品行为；
- 定量数据 + 定性案例。

## 8. 证据标签

每条关键判断使用以下标签之一：

- `OFFICIAL_CLAIM`：官方材料中的声明；
- `OBSERVED`：研究者实际观察；
- `THIRD_PARTY_EVIDENCE`：可核对的第三方资料；
- `INFERENCE`：基于多项证据作出的推断；
- `HYPOTHESIS`：尚待验证的假设。

并记录置信度：

- `High`：多源一致且可直接验证；
- `Medium`：证据较充分，但存在条件限制；
- `Low`：样本不足、信息陈旧或仅能间接推断。

## 9. 研究阶段

### Phase 1 — Research Design

研究问题、样本框架、评价指标、数据字段和来源政策。

### Phase 2 — Product & Company Mapping

建立产品与公司数据集，完成重点案例的能力和战略分析。

### Phase 3 — Talent Mapping

采集公开岗位样本，建立岗位族群、能力标签和目标公司地图。

### Phase 4 — Synthesis

完成执行摘要、完整报告、图表和可供面试讨论的核心结论。

## 10. 质量门槛

进入正式报告的结论必须满足：

- 能追溯到来源或体验记录；
- 明确区分事实、观察和推断；
- 标注数据日期与适用条件；
- 对争议性判断呈现反例或限制；
- 不通过伪精确评分掩盖证据不足。

## 11. 主要限制

- 产品迭代速度快，快照可能迅速过时；
- 个人试用受套餐、模型、地区和项目类型影响；
- 公开岗位不能完整代表企业内部真实组织需求；
- 商业公司披露的数据可能具有选择性；
- 不同产品的任务边界和权限不同，横向评分只能用于特定场景。
