## 1. 总体判断

完整报告草稿 v0.1 已具备一篇探索性研究的主体结构：研究问题明确，产品、瓶颈、岗位、能力框架与人才 Mapping 已形成逻辑闭环，并保留了反例、样本边界和证据限制。

当前不需要继续扩张新的核心框架。报告尚不适合直接标记为公开版 v1.0，主要原因不是研究内容不足，而是：

> **部分关键主张与底层证据之间的追溯成本仍然较高，少数命题的措辞强度也高于现有定向样本能够稳定支持的程度。**

公开前应优先完成证据治理、命题强度校准、正文压缩和阅读结构调整。

## 2. 发布前必须处理的问题

### 2.1 建立主张—证据索引

当前正文通常在章节末尾链接整个产品矩阵、瓶颈矩阵或 JD 编码文件，但没有逐项说明：

- 哪一条产品资料支持哪一项判断；
- 哪几份 JD 支持某个岗位原型；
- 哪一项陈述属于官方事实或公司主张；
- 哪一项属于样本归纳；
- 哪一项属于研究者推断或规范性建议；
- 哪些反例限制该主张的适用范围。

应新增 `data/claim-evidence-index-v0.1.csv`，至少包含：

| 字段 | 含义 |
|---|---|
| claim_id | 主张编号 |
| chapter | 所在章节 |
| claim | 主张原文或标准化表述 |
| claim_type | 事实／公司主张／样本归纳／研究推断／方法建议 |
| evidence_grade | A／B／C／D／E |
| supporting_sources | 产品、JD 或案例编号 |
| source_file | 仓库内证据文件 |
| counterevidence | 反例或限制 |
| publication_wording | 公开版允许使用的措辞 |
| status | 可保留／需降级／待补证／删除 |

该索引是进入公开版前最优先的产物。

### 2.2 校准六项研究假设

#### H1：项目可行边界扩张

现有证据主要由产品可委托范围扩大和一个个人实践案例构成，尚不足以证明普通用户群体普遍启动了过去不会考虑的项目。

公开版建议表述：

> **有限支持。产品资料证明可委托任务范围扩大；个人案例说明可行边界扩张的机制可能存在，但尚缺乏更广泛用户样本。**

#### H2：能力瓶颈迁移

这是目前证据相对充分的命题。产品资料直接显示规格、上下文、环境、权限和验证的重要性，岗位样本进一步显示企业正在配置评测、平台、安全、部署和采用责任。

公开版建议表述：

> **获得较强支持，但不同任务类型的瓶颈迁移方向并不一致。**

#### H3：岗位名称解释力下降

原命题包含两个不同判断：

- H3a：不同岗位名称可能解决结构相似的能力瓶颈；
- H3b：相同岗位名称在不同公司可能承担明显不同职责。

现有定向样本较好支持 H3a，但缺少足够的同名岗位配对样本来稳定检验 H3b。

公开版建议拆分：

> **H3a 获得支持：不同岗位名称可以解决结构相似的能力瓶颈。**  
> **H3b 证据不足：同名岗位的跨公司职责差异仍需更多配对样本。**

#### H4：连接型人才需求上升

当前“条件性支持”的方向基本准确，但“连接型人才”容易被理解为已经存在的统一行业类别。

章节标题建议改为：

> **连接型能力：在边界岗位中获得条件性支持**

公开版结论应限定为：产品、部署、采用、研究转化和组织运营等边界岗位更依赖跨边界转换能力；核心平台和深度工程岗位仍主要依赖专业技术能力。

#### H5：技术能力发生结构性变化

现有样本能够证明部分非核心研发和边界岗位更强调技术判断、集成、原型和验证，但不能证明整个 AI 人才市场发生统一变化。

公开版建议表述：

> **条件性支持。部分非核心研发和边界岗位的技术要求表现为技术判断、集成与验证责任；核心平台岗位仍保持较高专业工程门槛。**

#### H6：Agent 治理成为组织能力

“治理”需要拆解为已被观察到的具体责任：评测与完成证据、身份权限、审批、审计、发布门槛、停止和回滚。

公开版建议表述：

> **初步支持。样本产品与岗位中已经出现评测、权限、审计和发布控制责任，但尚不能认定企业已经形成统一的 Agent 治理模型。**

## 3. 岗位样本应进行分层说明

20 份 JD 不属于同一职业总体。公开版应明确分为三层：

| 样本层 | 岗位类型 | 主要分析用途 |
|---|---|---|
| S1 核心交付岗位 | Agent Harness、平台、评测、CI/CD、安全 | 分析 Agent 系统和工程交付能力 |
| S2 边界与采用岗位 | 产品、Deployed PM、AI Adoption、Product Operations | 分析产品、客户和组织连接责任 |
| S3 组织决策岗位 | People Research、Workforce Planning | 分析证据如何进入组织与人才决策 |

分层的目的不是建立行业标准分类，而是解释为什么技术平台岗位和 People 岗位会出现在同一研究中：它们承担的是完整组织闭环中的不同问题，而不是同一岗位市场。

## 4. 正文结构需要压缩

v0.1 中以下部分存在较多重复：

- 研究假设的阶段性检验；
- 主要结论；
- 最终结论。

公开版建议合并为“讨论、结论与局限”，依次回答：

1. RQ1—RQ5；
2. 六项假设的阶段判断；
3. 理论或方法贡献；
4. 反例和适用边界；
5. 研究局限；
6. 最终结论。

预计可压缩正文约 15%—25%，同时减少同一结论在不同章节重复出现。

## 5. 个人案例与目标岗位应用降级为附录

个人案例只承担机制解释，不承担证明作者完整胜任力或行业规律的任务。公开版建议：

- 附录 A：校园重建工具与 Movie Night 机制案例；
- 附录 B：AI 组织能力情报岗位的方法应用；
- 附录 C：主张、来源与编码索引。

主报告正文只需保留一段，说明研究方法可以应用到真实人才战略问题。

副标题建议由：

> 基于产品资料、公开招聘岗位与个人实践案例的探索性研究

调整为：

> **基于产品资料与公开招聘岗位的探索性研究**

个人案例继续以 E 级证据保留在附录。

## 6. 具体措辞修正

### 6.1 产品章节标题

“六条产品演进路线”实际描述的是六个产品，建议改为：

> **六个核心产品的演进概览**

产品路线可另行归纳为 IDE 中心、终端与 Harness 中心、代码托管工作流中心、云端自主执行与指挥中心。

### 6.2 企业岗位信号

将：

> 企业确实开始配置人员负责……

调整为：

> **本研究样本公司的公开 JD 显示，相关企业正在招聘人员承担……**

避免从 17 份 A 级 JD 直接推断整个行业。

### 6.3 能力原型名称

将“六类能力原型”统一改为：

> **六类探索性岗位能力原型**

明确这些原型是定向样本中形成的分析工具，而不是经过大样本验证的行业标准。

### 6.4 管理责任结论

将：

> Agent 不会消除管理……

调整为：

> **在本研究观察的 Coding Agent 场景中，Agent 化没有消除管理责任，而是使部分管理活动转向目标定义、执行边界、异常处理、验证和人机工作流。**

“执行可以被委托，但目标判断、风险承担和最终责任不能被完全委托”应标为研究者规范性判断 D，而不是行业事实。
